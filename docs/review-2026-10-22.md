## 1. 新发现的缺陷

### N1 自检删句后，引用列表没有同步 —— 用户会看到"正文里不存在的引用"

**位置**：[QaService.java](../server/src/main/java/com/ragkb/qa/QaService.java#L117-L127)、[EvidenceEvaluator.java](../server/src/main/java/com/ragkb/generation/EvidenceEvaluator.java#L244-L260)

`QaService` 在自检之后返回的是 `parsed.citations()`（**原始答案**里的全部合法编号），而展示文本是 `verdict.text()`（**被自检删剩的句子**）。两者在"某句被删、且该句是唯一携带某编号的句子"时不一致：

```
模型原文      = 第一句引用[E1]。第二句没有引用。
自检后展示文本= 第二句没有引用。
返回的引用    = [E1]
展示文本里是否还有 [E1] = false
```

**已在运行时复现**（独立探针，见第 5 节）。后果：

1. 前端 `cite-bar` 会渲染一个 `[E1]` 的引用按钮，但正文里没有任何可点的 `[E1]`；
2. `AnswerEval` 的"引用正确率"分母把这条已不存在的引用也算进去，指标被拉低/口径失真；
3. 与项目"每一句答案都能追溯"的核心承诺直接冲突。

**修法**：`Verdict` 增加"保留下来的编号集合"（或直接从 `kept` 句子的 `citations()` 汇总），`QaService` 用这个集合过滤 `parsed.citations()`；`AnswerEval` 同步改为消费过滤后的引用。配套补一条"部分句子被删、其中一句带唯一引用"的回归测试（当前 `QaServiceTest` 只有"全删"用例，`unsupportedEverythingRefuses`，覆盖不到这个分支）。

### N2 全局异常处理把**所有**客户端错误都变成 500

**位置**：[GlobalExceptionHandler.java](../server/src/main/java/com/ragkb/common/GlobalExceptionHandler.java#L51-L57)

`@ExceptionHandler(Exception.class)` 会抢在 Spring 的 `DefaultHandlerExceptionResolver` 之前接住所有框架异常，于是下面这些**本应是 4xx** 的请求全部返回 `500 服务内部错误`：

| 请求 | 实测结果 | 应有结果 |
|---|---|---|
| `POST /api/auth/login`，body 为 `{bad json` | 500 | 400 |
| `POST /api/auth/login`，空 body | 500 | 400 |
| `POST /api/auth/login`，无 `Content-Type` | 500 | 415 |
| `GET /api/auth/login`（方法不允许） | 500 | 405 |
| `GET /api/documents/abc`（路径参数类型错） | 500 | 400 |
| `POST /api/documents`（缺少 `file` part） | 500 | 400 |

这还会把客户端错误按 `ERROR` 级别打整页堆栈（实际日志里已经出现），淹没真正的 500。

**修法**：在 catch-all 之前显式处理 `HttpMessageNotReadableException`(400)、`MethodArgumentTypeMismatchException`(400)、`MissingServletRequestPartException` / `MissingServletRequestParameterException`(400)、`HttpRequestMethodNotSupportedException`(405)、`HttpMediaTypeNotSupportedException`(415)、`NoResourceFoundException`(404)；catch-all 只兜真正未预期的异常，并对 4xx 用 `WARN` 而不是 `ERROR`。

### N3 "答案支持率"把**自检失败**的题算成"有支撑"，指标会虚高

**位置**：[AnswerEval.java](../server/src/main/java/com/ragkb/eval/AnswerEval.java#L239-L242)、[EvidenceEvaluator.java](../server/src/main/java/com/ragkb/generation/EvidenceEvaluator.java#L238-L241)

自检调用抛 `ChatException` 时，`verify` 返回：

```java
new Verdict(false, Reason.CHECK_UNAVAILABLE, answer.sanitized(),
            0, judgeable.size(), true);   // kept = 全部句子
```

而 `AnswerEval.compute` 只判断 `verdict != null`，不判断 `verdict.unavailable()`：

```java
judged += answer.verdict().kept() + answer.verdict().dropped();
kept   += answer.verdict().kept();
```

于是**自检挂掉=全部句子算通过**。数据库抖一下或模型超时，答案支持率会从 0.96 升到 1.00，而且从输出上完全看不出来 —— 与已经修掉的 BUG-11（通道故障记成拒答）是同一类错误。

**修法**：`compute` 里把 `verdict.unavailable()` 的题从支持率分母中剔除，或单列一行"自检不可用 N 题"；`describe` 也要显示"自检失败"而不是"引用 x/y 命中"。补一条 `CHECK_UNAVAILABLE` 的单测（`AnswerEval` 目前**没有任何测试**）。

### N4 自检调用的 token 没有计入"用量"，报告里的成本少算近一半

**位置**：[EvidenceEvaluator.java](../server/src/main/java/com/ragkb/generation/EvidenceEvaluator.java#L288-L289)、[QaService.java](../server/src/main/java/com/ragkb/qa/QaService.java#L121-L127)、[AnswerEval.java](../server/src/main/java/com/ragkb/eval/AnswerEval.java#L237-L238)

`verify` 调 `checker.complete(...)`，但只取 `response.content()`，把 `promptTokens/completionTokens` 丢掉；`QaAnswer` 里的 token 只来自生成那一次。`docs/eval-baseline.md` 写"用量 86071 token / 109 秒 | 59 题，含生成与自检两次调用"——**时间含两次调用，token 只含一次**。

粗略核对：单题生成输入约 1235、输出约 71；自检输入还有一份材料（约 1000 token）+ 句子列表，输出几十 token。59 题的真实总用量应显著高于 86k。

**修法**：`Verdict` 增加自检的 `promptTokens/completionTokens`（或让 `verify` 接受一个累加器），`QaAnswer` 增加 `selfCheckPromptTokens/selfCheckCompletionTokens` 字段，报告里分别列出"生成 / 自检 / 合计"。在此之前，至少把报告口径改成"**生成调用** token（不含自检）"。

### N5 BCrypt 的 72 字节上限没有在入参校验，长中文密码注册直接 500

**位置**：[AuthRequest.java](../server/src/main/java/com/ragkb/auth/AuthRequest.java#L21-L22)、[AuthService.java](../server/src/main/java/com/ragkb/auth/AuthService.java#L43-L56)

`@Size(min = 8, max = 64)` 数的是**字符**，BCrypt 限制的是 **UTF-8 字节**：

```
chars=24 bytes=72 -> OK
chars=25 bytes=75 -> IllegalArgumentException: password cannot be more than 72 bytes
```

实测：用 30 个汉字（90 字节）注册，服务端返回 `500 服务内部错误`；登录侧同样会走 `passwordEncoder.matches`，需一并加校验，否则超长口令的登录也会走到同一条异常路径。对中文用户来说，25 个汉字的口令并不罕见，这是**注册链路的可用性**问题，不只是"边界情况"。

**修法**（二选一）：
- 入参校验 UTF-8 字节数 ≤ 72，超了返回 400 并给出明确文案；
- 或先做一次 SHA-256（Base64）再交给 BCrypt，从而支持任意长度口令（需同时改注册与登录，且要写迁移说明）。

同时把 `@Size(max=64)` 的中文语义写进注释，避免下一个人以为 64 字就是 64 字。

### N6 前端点旧答案的引用，会打开**最新一条**同编号答案的原文

**位置**：[ChatView.vue](../web/src/views/ChatView.vue#L85-L101)

```js
const owner = [...messages.value].reverse()
  .find((m) => m.citations?.some((c) => c.label === label))
```

`onAnswerClick` 只拿到 `label`，没有拿到"被点击的是哪条消息"，于是全局从新到旧找第一个含该编号的消息。同一会话里问三个问题、每条都有 `[E1]` 时，点第一条答案里的 `[E1]`，抽屉展示的是**第三条**的切片。注释里已经写明"同一编号在不同回答里指向不同切片，不能全局查"，但实现恰好是全局查。

**修法**：模板改为 `@click="onAnswerClick($event, message)"`，在方法里用当前 `message.citations` 查；找不到再回退到全局并提示。

### N7 PDF 编号列表项被误判成标题，污染 `sectionPath`

**位置**：[PdfParser.java](../server/src/main/java/com/ragkb/parse/PdfParser.java#L34-L38)、[PdfParser.java](../server/src/main/java/com/ragkb/parse/PdfParser.java#L84-L95)、[PdfParser.java](../server/src/main/java/com/ragkb/parse/PdfParser.java#L129-L130)

`headingLevel` 先判"字号放大 / 编号模式"，**再**判 `LIST_ITEM`；而 `NUMBERED_HEADING` 的 `\S+$` 不允许多词，所以：

- `1. Install the JDK first`（多词）→ `LIST_ITEM`，正常；
- `2. Troubleshoot`（单词）→ **`HEADING` level 3**（实测）；
- `1. 首先安装JDK`（中文无空格）→ 同样会命中 `HEADING`。

中文编号列表绝大多数没有内部空格，因此这条在实际中文 PDF 上比英文更容易触发。后果：列表项进入章节栈，`sectionPath` 变成 `"第二章 > 1. 首先安装JDK > ..."`，切片边界与"所属章节"全部失真（内容不丢，但结构语义错）。

**修法**：把 `LIST_ITEM` 判断提到 `NUMBERED_HEADING` 之前；或给 `NUMBERED_HEADING` 加一条"不能是列表项"的排除（例如要求编号后是短标题、且不以列表符号/序号形式出现）。补一条"正文相同字号 + 编号列表项"的 PDF 用例。

### N8 异步入库线程池：无界队列 + `shutdownNow` + 无启动恢复

**位置**：[IngestTrigger.java](../server/src/main/java/com/ragkb/document/IngestTrigger.java#L32-L50)

- `Executors.newFixedThreadPool(2)` 用的是**无界** `LinkedBlockingQueue`：突发上传会无限堆积，没有背压，也没有"队列深度"指标；
- `@PreDestroy` 用 `shutdownNow()`：正在解析的文档会被中断，状态停在 `PARSING`，没有补偿；
- 应用重启后，停在 `UPLOADED`/`PARSING` 的文档不会自动重跑，只能人工点"重新切片"。

**修法**：有界队列 + `CallerRunsPolicy`（或拒绝并标记 FAILED + 可重试）；`shutdown()` + `awaitTermination(30s)`；启动时扫描 `status in ('UPLOADED','PARSING') and updated_at < now() - interval '5 minutes'` 的文档重新触发（或至少标为 FAILED 并写清原因）。

### N9 Spring Boot 自动创建了内存默认用户，启动日志里打印生成密码

**证据**：应用启动日志

```
WARN ... UserDetailsServiceAutoConfiguration :
Using generated security password: <uuid>
...
Global AuthenticationManager configured with UserDetailsService bean with name inMemoryUserDetailsManager
```

JWT 应用并不需要 `UserDetailsService`。当前 HTTP Basic 未开启，所以这个默认用户登不进来，但：

1. 每次启动日志里都有一条"看起来像凭据"的字符串，违反"日志不打敏感字段"的自我约定；
2. 将来任何人加了 `httpBasic()` / `formLogin()`，默认 `user` 账号就会成为后门；
3. `SecurityConfig` 的默认拒绝语义会被这个"额外身份来源"稀释。

**修法**：`@SpringBootApplication(exclude = UserDetailsServiceAutoConfiguration.class)`，或在配置里显式声明只使用 JWT 的 `AuthenticationManager`。同时把"应用里只有一个身份来源"写进 `SecurityConfig` 注释。

### N10 CORS 是半套配置：`OPTIONS` 放行了，但没有 `Access-Control-Allow-*`

**位置**：[SecurityConfig.java](../server/src/main/java/com/ragkb/auth/SecurityConfig.java#L55-L61)

实测预检：

```
OPTIONS /api/qa   -> 200
Allow: GET, HEAD, POST, PUT, DELETE, OPTIONS, TRACE, PATCH
（没有 Access-Control-Allow-Origin / -Methods / -Headers）
```

代码里有 `.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()`，注释说"拦掉它会让浏览器直接报跨域错"，但因为没有 `CorsConfigurationSource`，浏览器仍会报跨域。这是一个"看起来处理了、实际没处理"的配置，比不放行更容易误导。

**修法**：要么补 `CorsConfigurationSource` + `.cors(Customizer.withDefaults())`（允许来源从配置读，别写 `*` + 凭据），要么删掉这行并明确写"仅同源部署（Vite 代理 / 反代）"。

### N11 切片参数实际上不可配置 —— 与"参数由实测推导、改参数要重跑"的方法论矛盾

**位置**：[StructureAwareChunkSplitter.java](../server/src/main/java/com/ragkb/chunk/StructureAwareChunkSplitter.java#L47-L57)、[ChunkingProperties.java](../server/src/main/java/com/ragkb/chunk/ChunkingProperties.java#L42-L44)

`@Component` 的 `StructureAwareChunkSplitter` 有两个构造器（无参 + 带 `ChunkingProperties`），Spring 在无 `@Autowired` 时选**无参**那个，于是永远用 `ChunkingProperties.defaults()`；`ChunkingProperties` 也没有 `@ConfigurationProperties` 绑定，`application.yml` 里没有任何 `app.chunking.*`。结果是：

- 改 target/max/overlap 必须改代码、重新编译；
- 实验 E4（切片参数推导）无法只靠配置切换；
- 预览工具、单测、线上三处都各自 `new` 默认值，无法保证同口径。

**修法**：给 `ChunkingProperties` 加 `@ConfigurationProperties(prefix = "app.chunking")` 并在 `StructureAwareChunkSplitter` 上显式 `@Autowired` 带参构造器；`application.yml` 增加三项（含注释：改它们必须重跑评估）。同时保留无参构造给预览工具。

### N12 评估工具的装配与线上会漂移

**位置**：[AnswerEval.java](../server/src/main/java/com/ragkb/eval/AnswerEval.java#L109-L114)、[RetrievalComparison.java](../server/src/main/java/com/ragkb/eval/RetrievalComparison.java#L72-L80)

- `AnswerEval` 手工 `new`：`EmbeddingProperties(..., 512, 10, ...)`、`new PromptBuilder(new TokenCounter())`（默认 5/2000）、`channelLimit=20`，**不读** `EMBEDDING_BATCH_SIZE` / `GENERATION_MAX_EVIDENCE` / `GENERATION_MAX_CONTEXT_TOKENS` / `CHAT_TEMPERATURE` 等配置；线上改一个预算，评估仍按旧预算跑，指标会"莫名其妙"变化。
- `RetrievalComparison` 的 HYBRID 用 `limit * 2` 作为每通道候选（40/40），而线上 `QaService` 是 `channelLimit`（20/20）。我实测两组结果完全一致（所以现有数字没被污染），但这是"现在恰好一样"，不是"设计上一致"。

**修法**：抽一个 `EvalAssembly`（或直接复用 `AiProperties`/`GenerationProperties` 的绑定值），让评估与线上共用同一套构造函数；`RetrievalComparison` 的通道池改为与线上一致（或显式命名 `HYBRID(40/40)` 并在文档里说明）。评估报告里记录"本次运行用的配置快照"。

## 3. 优化建议（按收益排序）

### 3.1 可靠性与并发（最高性价比）

1. **用 Java 25 虚拟线程替换两个固定池**。`HybridRetriever.defaultExecutor()` 是 8 线程固定池，每个问答占 2 个；4 个并发问答就饱和，而 `orTimeout` **不会取消**底层任务（已知 P2-13），卡住的 JDBC 线程会一直占着。建议：
   - `spring.threads.virtual.enabled=true`（Tomcat 虚拟线程）；
   - `HybridRetriever` 的 executor 改为 `Executors.newVirtualThreadPerTaskExecutor()`；
   - `IngestTrigger` 同样改虚拟线程，再配一个有界信号量限制并发解析数。
   这是"Java 25"这个选型最值得展示的地方，也顺手修掉 P2-13。
2. **超时要在底层生效**：`orTimeout` 只完成 future，不打断 HTTP/JDBC。给 `JdbcTemplate` 设 `queryTimeout`（例如 2 秒），给 `HttpRequest` 已有 `timeout`；如需更严，用 `future.cancel(true)` + 可中断的 `HttpClient.send`/JDBC。
3. **`/api/qa` 加 bulkhead + 请求超时**：单题最坏 3 次生成 × 60 秒 + 3 次自检 × 60 秒 = 6 分钟；200 个 Tomcat 线程同时压进来会打爆配额和内存。建议一个 `Semaphore(8)` + 90 秒总超时，超时返回 503 + `Retry-After`。
4. **入库并发**：同一文档的自动触发与手动"重新切片"可能同时跑，`replaceAll` 的 delete+insert 在唯一索引上可能让后到者失败并把状态写成 `FAILED`（尽管先到者已成功）。建议 `SELECT ... FOR UPDATE` 锁 documents 行，或 `UPDATE ... SET status='PARSING' WHERE id=? AND status<>'PARSING'` 用受影响行数做互斥。
5. **`/health` 拆 readiness**：`SELECT 1` + 可选 Key 检查；否则容器编排会把"能连上但答不了"的实例当健康。

### 3.2 性能

6. **切片批量插入**：[ChunkStore.replaceAll](../server/src/main/java/com/ragkb/document/ChunkStore.java#L39-L57) 逐条 `insert`；改成 `batchUpdate`（或单条多值 INSERT）。200+ 片的文档能从 200 次往返降到 1~2 次。
7. **上传去掉双写**：[DocumentService.upload](../server/src/main/java/com/ragkb/document/DocumentService.java#L70-L88) 先写临时文件、再 `Files.copy` 到存储；50MB 文件写两遍。可把临时文件建在存储根下、算完摘要后 `Files.move(ATOMIC_MOVE)`；或边算摘要边写目标临时名，最后改名。
8. **PDFBox 用临时文件模式**：`PDDocument.load(InputStream)` 全量进堆，50MB 扫描件容易 OOM；改 `PDDocument.load(content, MemoryUsageSetting.setupTempFileOnly())`，并给解析加超时/页数上限。DOCX 侧用 `ZipSecureFile.setMaxEntrySize` 防 zip bomb。
9. **关键词打分只算一次**：[JdbcKeywordRetriever](../server/src/main/java/com/ragkb/retrieval/JdbcKeywordRetriever.java#L67-L85) 的 score 子查询对每个候选再跑一遍 `regexp_matches`。可改成 `LATERAL (SELECT array_agg(...) ...)` 或 CTE，一次算完复用。42 行无感，10 万行有感。
10. **给 JDBC 配 `statement_timeout`**：正则/trigram 在坏查询上可能长时间占用连接；Hikari 的 `connection-timeout` 不是查询超时。
11. **`DocumentTitles` 换成有界缓存**：[GenerationConfig](../server/src/main/java/com/ragkb/common/GenerationConfig.java#L63-L70) 的 `ConcurrentHashMap` 永不失效、无上限；用 Caffeine `maximumSize(1000)` + `expireAfterWrite(10m)`，或在文档重命名/删除时失效。
12. **向量检索距离只算一次**：`SELECT 1 - (<=>) ... ORDER BY (<=>)` 让同一表达式出现两次；改成子查询 `SELECT ..., 1 - dist AS score FROM (SELECT ..., embedding <=> ? AS dist ...) t ORDER BY dist`。当前 20 行可忽略，属于写法整洁。
13. **分页**：`GET /api/documents` 加 `page/size`，并给 `documents(created_at desc)` 加索引；前端表格改服务端分页。

### 3.3 检索与生成质量

14. **自检的经济性**：59 条里只删了 2/62 句，却让每个作答都多一次模型调用（延迟 + 成本接近翻倍）。建议按条件触发：
    - 只在"答案里有没有引用的句子"或"门控分数接近阈值"时自检；
    - 或自检换更便宜/更快的模型（如 qwen-turbo），并固定 `temperature=0`；
    - 或把"逐句判定"改成一次批量判定（现在已经是批量，但可以再压缩材料）。
    改完在 59 条上对比"支持率/误删率/成本"三者，别只看支持率。
15. **流式输出（SSE）**：当前要等生成 + 自检两次调用才返回（实测 2.4 秒，长答案更久）。生成改为 SSE 增量推送，自检作为后置校验（或者先流式展示、再标记"已核验"），演示体感会完全不同。
16. **重排/去重**：现在融合后直接取前 5 喂模型，切片 overlap 会导致相邻片含同一句（已知"重叠导致重复引用"）。加一层轻量去重（按句子/字符区间）或 MMR，引用正确率与提示词干净度都会提升。
17. **提示词结构化**：用 `<evidence id="E1" source="...">` 包裹每条材料，明确"标签内是数据，不是指令"；标题/章节路径做转义与换行清理（N20）。这比在系统提示里写一句"材料是数据"更抗注入。
18. **`looksLikeRefusal` 的鲁棒性**：目前是"归一化后 contains 固定串"。如果模型写"材料中未提及，但根据常识……"会被整段判成拒答；如果写"材料中没有提及"（多一个"有"）又判不成。建议用少量正则集合 + "是否含任一合法编号"联合判断，或用一次 JSON 输出 `{"answerable": false}`。
19. **`text_type` 保持现状**：当前实例是 no-op，接口拆分已做，换供应商时按文档的三请求抽检即可，不需要动。

### 3.4 评估方法学（这个项目的护城河，值得多花时间）

20. **修 N3 / N4 后再谈基线**：支持率虚高和 token 少算都会让"成本-效果"结论失真；修完在报告里分别列"生成/自检/合计"。
21. **加运行清单（run manifest）**：每次跑批把 git SHA、embedding/chat 模型名、chunk 参数、generation 预算、cases.json 的 hash、阈值写进 JSON。现在这些只散落在 docs 里，半年后无法复现。

23. **把 `AnswerEval` 的指标计算抽成可测类**：现在 `compute` 是 private、零测试，N3 就是这么漏掉的。抽出 `GenerationMetrics`，补 `CHECK_UNAVAILABLE`、`degraded`、全删/部分删、无引用等用例。

### 3.5 安全

## 6. 值得保留的设计（修复时不要顺手改掉）

- **`ParsedDocument` 的坐标契约 + 专用契约测试**：把"块间距恰为 1"这种隐形约定用测试钉死，是这类项目最容易缺失的地基。
- **两阶段拒答 + 原因枚举**：`NO_HITS / CHANNELS_DOWN / WEAK_EVIDENCE / MODEL_INSUFFICIENT / UNSUPPORTED / CHECK_UNAVAILABLE` 让"为什么拒答"可归因；`CHANNELS_DOWN` 与 `FAILED` 的映射尤其正确。
- **通道降级语义**：单路超时/异常返回空 + `degraded` 标记，不把故障伪装成"材料里没有"；跑批把降级题从拒答指标剔除 —— 这是很多团队做不到的诚实。
- **`PromptBuilder` 的预算按拼接后实测**：吸收了"token 不可相加"，并且在边界上做了实测而非朴素加法。
- **`CitationParser` 的"形态宽、存在性严"**：容忍 `[ E1]`、全角括号、`E01`，但不放过不存在的编号；`[2026, 10]` 的处理是对的。
- **`HttpPoster` 抽象**：让重排、维度校验、重试分级都能离线测试；这是整批代码里最值钱的设计决策之一。
- **`docs/eval-baseline.md`**：把"指标不能归因于门控"、"答案支持率由自检模型判定"写在明面上；这种自我免责比漂亮的数字更有价值。
