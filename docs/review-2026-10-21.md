## P0 · 实证确认的 bug

### BUG-1 PdfParser 丢失"坐标偏移分词"的空格

**现象**：一页 PDF 中两行内容等价——
- 行 1：`showText("alpha beta gamma")`，词间有真实空格字形；
- 行 2：`showText("alpha")` + 坐标跳开 60pt + `showText("beta")`，**没有空格字形**，词边界纯靠坐标间距表达。

用 `PdfParser` 解析，输出：

```
[PARAGRAPH] text=[alpha beta gamma
alphabeta]        ← 行 2 的空格丢失
```

**根因**（已用 `javap -c` 反汇编 pdfbox-2.0.32 确认）：
`PDFTextStripper.writeWordSeparator()` 把分词空格**直接写入 output Writer**，调用链是
`writeLine() → writeWordSeparator() → Writer.write(wordSeparator)`，
全程不经过 `PdfParser` 覆写的 `writeString(String, List<TextPosition>)`（PdfParser.java:198）。
而 `LineCollectingStripper.lineBuffer` 只从后者收集文本，于是 PDFBox 依据坐标间距判定出的词间空格全部丢失。

**当前未暴露的原因**：Word 导出 PDF 与现有中文样本的空格来自字形（样本里「正 文」即此类）。但 LaTeX 排版的 PDF 词间几乎全靠 TJ 偏移表达，一旦上传此类 PDF（对应验收标准"上传一份 20 页 PDF"）必踩。

**连锁影响**（比空格本身严重）：
1. 关键词检索（ILIKE / pg_trgm 方案）在这种 PDF 上英文词全粘连，命中率崩塌；
2. `sentenceBounds`（StructureAwareChunkSplitter.java:353）规定英文 `.` 仅在后面是空白时才算句末——无空格则英文**永不切句**，hardSplit 退化为窗口硬切，等于 D4 验收口径失效。

**修复方向**：同时覆写 `writeWordSeparator()` 向 `lineBuffer` 追加空格。注意两点：
- `flushLine()` 已对整行 strip，首尾触发无影响，但需考虑词间多次触发的折叠（PDFBox 默认词分隔符是单个空格，一般无需额外处理，建议实测确认）；
- 在 `BinaryParserStructureTest` 补一个"同一行内多个 showText、坐标跳开"的用例——现有英文测试整行是单个 showText，覆盖不到该分支。

### BUG-2 merge() 的全标题缓冲可突破 maxTokens 硬上限

**现象**（默认参数 target=300 / max=400 实测）：一个 64 token 的标题 + 一个 384 token 的正文段（各自均 < max），产出：

```
chunk#0 tokens=449  ← 超过硬上限 400
```

**根因**：StructureAwareChunkSplitter.java:135-139——"缓冲里全是标题时不封口"把 `overTarget` 置 false 后直接 `buffer.add(unit)`，此后**没有任何路径检查 `bufferTokens > max`**。这违反了 `ChunkSplitter` 接口自己声明的硬约束③（单片不得超上限），`assertInvariants` 遇到此类输入必挂。

**当前未暴露的原因**：现有语料最长段落 184 token，184 + 标题 < 400。但 `ChunkingProperties` 注释只写了"max 必须大于语料最长段落"，实际隐含约束是 **max > 最长段落 + 前导标题串 token 和**。这直接打在"切片参数由语料实测推导"的卖点上：换一份语料（长标题或长段落）即触发，且是**静默超限**——不跑校验就发现不了。

**修复方向**（语义取舍需定案）：
- 方案 A：`buffer.add` 之后若 `bufferTokens > max` 强制封口，把当前 unit 留给下一片（或触发 hardSplit）；
- 方案 B：接受"标题并入超长块第一片"的语义，让 hardSplit 的 `reservedTokens` 逻辑同样覆盖这条路径（现有 hardSplit 分支已正确处理 reserved，唯独全标题缓冲分支漏了）；
- 无论选哪个，把"max > 最长段落 + 前导标题串"写进 `ChunkingProperties` 的注释与校验提示，并补一条单测：标题串 + 接近 max 的正文段。

## P1 · 设计 / 口径问题（建议评估集扩到 40 组之前定案）

### ISSUE-3 MULTI_HOP 用例与命中判据自相矛盾

`EvalCase.matches` 要求**单个切片**包含全部 expectedKeywords，但 c05（["量纲完全不同","归一化"]）、c06 的题型语义就是跨段。若两个关键词被切进不同片，该用例永远未命中，recall 被系统性拉低且原因不可见。
三选一：
1. MULTI_HOP 判据改为"前 K 片的并集覆盖全部关键词"（推荐，与题型语义一致）；
2. 标注时保证关键词必然同片（限制标注自由度）；
3. 把这两条用例改成 FACTOID。
baseline 产出前必须定，否则前后不可比。

### ISSUE-4 文档以标题结尾会产出"只有标题"的切片

`merge()` 末尾的 `flush(drafts, buffer, document)` 没走 `takeTrailingHeadings` 逻辑。文档最后一块是标题时，尾片只含标题，违反接口声明的"不产出只有标题的碎片"。影响小，但硬约束要么守住要么明确改口径（文档末尾的孤立标题允许成片）。

### ISSUE-5 两套"可回溯"校验口径不一致

- 单测 `assertInvariants`：`document.slice(...) == chunk.content()`，精确相等；
- `StructurePreview.contentMatchesSource`：`strip()` 后对比，允许首尾空白差异。

工具口径松于测试口径，会漏报真实的边界不一致。切片内容本就来自 `document.slice()`，两者统一为精确相等更严且无成本。

### ISSUE-6 DocumentController.list() 绕过 service

代码里已有 FIXME，判断成立：列表一旦要加过滤条件（如"只看解析成功的"），业务规则会散落进 controller。建议在检索模块接入前后顺手收掉，避免分层纪律破窗。

## P0 · 必须在评估基线（E1）之前解决

### BUG-5 查询与文档未区分 `text_type`，检索质量直接受损

**位置**：`DashScopeEmbeddingClient.buildRequestBody()` —— `parameters` 只带 `dimension`，从不带 `text_type`；`VectorRetriever.search()` 用同一个 `embed()` 向量化用户问题和入库文档。

**依据**（DashScope 官方文档原文）：检索是**非对称任务**，"为了达到更好的检索效果建议区分查询文本(query)和底库文本(document)类型"——query 生成"标题式"向量、方向性更强，document 生成"正文式"向量、信息更全。两边都用默认 document，短查询对长文档的匹配精度会差于正确用法。

**为什么是 P0**：这直接影响 recall@5 / MRR——恰是评估集要测的核心指标。基线若在错误口径上跑出来，后续所有对比实验（RRF 的 k、关键词方案对比）都会被这个系统性偏差污染。而且它不报错、只会让数字"莫名偏低"，非常隐蔽。

**修复方向**：`EmbeddingClient` 接口拆成 `embedQuery(String)` 与 `embedDocument(String)`（或加 `TextType` 参数），DashScope 实现在 `parameters` 里带 `text_type`（HTTP 调用时放 parameters 对象内，官方已确认）。`VectorRetriever.search` 走 query 侧，入库侧走 document 侧。接口契约变化需同步 `VectorRetrieverTest` 与 `TokenCalibration`（校准用 document 侧即可）。

### BUG-6 配置装配断裂：`fromEnvironment()` 读不到 `.env`，yml 新增配置是死配置

**现象**（两处叠加）：

1. 已确认**没有任何 @Configuration/@Bean** 装配 `EmbeddingClient` / `VectorStoreRepository` / `VectorRetriever`——组件齐了但没接线，这个本身符合按天推进的计划，不算 bug；
2. 但 `EmbeddingProperties.fromEnvironment()` 读的是 `System.getenv()`，而项目用的 spring-dotenv **只把 `.env` 注入 Spring 的属性解析（`${VAR}` 占位符），不会写进进程环境变量**。将来装配时若按这个方法名的直觉走 Spring 路线，`.env` 里明明配了 `DASHSCOPE_API_KEY`，运行时却报"缺少 DASHSCOPE_API_KEY"——因为 `System.getenv` 根本看不见 `.env` 文件（JVM 启动后进程环境不可变，任何库都加不进去）。

**同一根因的第二表现**：application.yml 新增的 `app.ai.dashscope.*` 六个键**没有任何代码绑定**（无 @ConfigurationProperties、无 @Value）。现在改 yml 里的 `embedding-batch-size` 不会有任何效果——是一份"看起来在生效"的死配置。

**附带矛盾**：yml 注释写"宁可在这里写死也不要让它看起来可配"，但同一行 `${EMBEDDING_DIMENSION:512}` 恰恰让它可配。若有人配成 1024：客户端维度校验通过（与 properties 一致）→ API 费用已花 → DB 的 `CHECK (dim = 512)` / `vector(512)` 才拦截。防线放在了花钱之后。

**修复方向**：装配时用 `@ConfigurationProperties(prefix = "app.ai.dashscope")` 绑定 yml（api-key 占位符走 spring-dotenv 才是活路），`fromEnvironment()` 保留给命令行工具并在 Javadoc 里写明"只读进程环境变量，读不到 .env——命令行使用前需 `export` 或脚本内 `source .env`"。`eval-run.sh` 将来接真实检索时同样受此影响。

## P1 · 中等

### BUG-7 `sleepBeforeRetry` 吞掉中断后继续重试

`callWithRetry` 里 `post()` 抛 `InterruptedException` 的路径处理正确（还标志、抛出）。但退避等待中被中断时（DashScopeEmbeddingClient.java:191-197）：捕获、恢复标志、**返回继续循环**。下一次 `post()`（JDK HttpClient 不主动检查已置位的中断标志，只有阻塞等待时才响应）可能照常发出请求——中断发生后至少多发一次外部调用，关闭/超时路径的语义不可预期。修法：`sleepBeforeRetry` 返回 false 时直接抛 EmbeddingException("向量化被中断")，与 post 路径对齐。

### BUG-8 `search` 不按 model 过滤，schema 注释的承诺没有兑现

schema.sql 写明存 `model` 列是为了"换了模型之后能分辨哪些行是旧模型算的，**避免混用导致排序失真**"——但 `SEARCH_SQL` 没有 `WHERE e.model = ?`。换模型重刷期间，新旧两组向量同库参与排序，余弦相似度跨模型没有可比性，检索结果失真——正是注释声称要防的事。当前单模型不触发，属于"注释承诺了、代码没兑现"。修法：search 加 model 参数（或按 repository 构造时注入的当前模型过滤），顺带能在换模型时只搜新向量。

## 3. 新发现：BUG-2 的修复有残留边界漏洞（BUG-9，已实证）

**响应报告自己发现了"token 数不可相加"（48+352 各自计数=400，拼接实测=401），但只把它用在修复内部的预算回调上——触发条件本身用的仍是朴素加法**：

```java
boolean headingsPlusUnitTooLarge =
        !containsBody(buffer) && bufferTokens + unitTokens > properties.maxTokens();
```

朴素和**恰好等于** max（不大于）时不触发修复路径，随后 flush 产出的切片按实测计数已经超限。

**实证**（`/tmp/pdfprobe/Probe4.java`，默认参数 max=400）：

```
head=49 + body=351, 朴素和=400 (不大于 400,不触发修复)
拼接后实测 token = 401  ← 超限
chunk#0 tokens=401  ← 超过硬上限!
```

新增回归测试 `headingPlusNearMaxBodyNeverExceedsMax` 用的是"标题约 48 + 正文约 400"——朴素和明显大于 max，恰好错过边界带 `[max-δ, max]`（δ 为拼接边界带来的增量，实测 1~2 token/边界）。

`tokenCounter.count(document.slice(buffer.get(0).block().charStart(), unit.block().charEnd())) > max`
——精确、无余量可拍。（用"max 减安全余量"也能堵，但余量本身是拍的，与本项目"参数不拍脑袋"的原则相悖。）

### BUG-10 答案正文里的数字方括号被静默删除（已实证）

**实证**（`/tmp/pdfprobe/Probe5.java`，提示词含 E1/E2/E10）：

```

sanitized: "该规范于发布[E1]。第二句话引用[E2]。"   ← 日期被整段删除
unknown:   [E2026]
```

根因：`labelsOf` 接受纯数字并列（`[2026, 10]` → E2026, E10），`markerAt` 认形态不认存在性；
存在性校验把整条标记判为"编造"，展示文本里整条删除。**本意是防死链，代价是把答案里的真实数据（日期、区间、表格引用）从用户可见文本里删掉**——raw 还在，但用户看到的 sanitized 缺字，排查极难发现。同理 `[1]` 会被误记成对 E1 的引用（引用正确率会虚高）。

**修法方向**（不改语义，只收紧形态）：括号内**至少一个 part 带 E/e 前缀**才认作引用标记——纯数字并列不当引用处理。若担心 `[E1]` 被模型写成 `[1]`，可用数据验证：基线里"编造编号 0 次"说明模型完全按提示词写了 E 前缀，收紧形态没有损失。

## P1 · 结构性问题（建议处理）

### ISSUE-21 JwtAuthFilter 被注册了两次，功能正常靠的是两个巧合

`JwtAuthFilter` 同时是 `@Component`（被 Spring Boot 自动注册进 servlet 容器全局过滤器链）**和** 被 `SecurityConfig.addFilterBefore` 注入 security chain——**同一实例，两处注册**。

功能验证通过（195 测试全绿），但"没出事"依赖两个未声明的巧合：
1. **注册顺序**：`springSecurityFilterChain` 的注册 order 是 -100，先于自动注册的 filter bean（默认最低优先级）。security chain 里的那份先执行并设置认证；全局链里的那份后执行时被 OncePerRequestFilter 的 already-filtered 标记跳过。若将来有人给 JwtAuthFilter 加 `@Order` 提升优先级，或调整注册方式，全局那份将先跑——它设置的 `SecurityContextHolder` 认证随后会被 security chain 的 `SecurityContextHolderFilter` 覆盖为空，而 chain 内那份又被 already-filtered 跳过——**全部接口静默 401**。
2. **幂等性**：本 filter 只做无副作用解析，跑两次不会错（类注释也写了这一点）。

**修法**（标准做法二选一）：加一个 `FilterRegistrationBean<JwtAuthFilter>` 并 `setEnabled(false)` 显式禁用自动注册；或去掉 `@Component`，在 SecurityConfig 里 `@Bean` 声明并用 `FilterRegistrationBean` 包装。同时把"只能注册一次"写进类注释——现在注释解释了为什么用 OncePerRequestFilter，但没解释双重注册这个真正的坑。

### ISSUE-22 测试套件的环境依赖自相矛盾（已实测 BUILD FAILURE）

`SecurityChainTest` 注释写明："库没起时本类会整体失败——这是有意的：认证链路没法离线验证，与其 skip 掉假装通过，不如让它红。" 但项目对真库用例的既有模式是 **Assumptions 跳过**（JdbcVectorStoreRepositoryTest / JdbcKeywordRetrieverTest，第四批响应里还专门强调"不会把'没跑'混成'通过'"）。

**实测**（Docker 未启动时跑 `mvn test`）：

```
Tests run: 195, Failures: 0, Errors: 7, Skipped: 6    BUILD FAILURE
（7 个 Error 全部来自 SecurityChainTest 的 ApplicationContext 加载失败，
 根因是 dataSourceScriptDatabaseInitializer 连不上库）
```

## P0 · 登录与注册接口 100% 返回 500（已实证复现）

### BUG-29 MyBatis 缺 UUID TypeHandler，刷新令牌写入必炸

**现象**（起真实服务 `POST /api/auth/register`，curl 复现）：

```
{"code":500,"message":"服务内部错误"}    http=500
```

服务端堆栈（关键行）：

```
java.lang.IllegalStateException: Type handler was null on parameter mapping
for property 'familyId'. It was either not specified and/or could not be found
for the javaType (java.util.UUID) : jdbcType (null) combination.
  ... RefreshTokenMapper.insert
  ... RefreshTokenService.issue(RefreshTokenService.java:131)
  ... AuthService.issueSession → AuthService.register
```

**根因**：`RefreshTokenEntity.familyId` 类型是 `java.util.UUID`，而 MyBatis 默认没有注册 UUID → PostgreSQL `uuid` 的 TypeHandler（MyBatis 官方仅内置 JDBC 标准类型；PG 方言的 UUID 映射需 `mybatis-typehandlers-jsr310` 之外的第三方包或自定义 handler）。`mapper.insert(entity)` 在参数绑定时直接抛 `IllegalStateException`。

**影响面**：`register`/`login` 都要经 `issueSession` → `issueNewFamily` → `insert` —— **所有注册与登录全部 500**。刷新令牌功能整体不可用，`refresh`/`logout` 无从谈起。这是"提交信息写着'测试全过'但核心功能全挂"的典型：见下条。

**为什么 231 个测试没抓到**——两层漏检，都是测试策略的结构性盲区：
1. `RefreshTokenServiceTest`（8 条，全绿）**mock 了 RefreshTokenMapper**——`mapper.insert` 被替换成 answer 桩，MyBatis 参数绑定这一层从未被走过；
2. 本该抓住它的 `SecurityChainTest`（真容器真 HTTP，`registerThenAccess`/`loginFailuresLookIdentical`/`refreshRotatesAndRevokesFamilyOnReplay` 三条**恰好就是依赖注册成功的用例**）在**数据库未启动时整类 skip**（第六批 ISSUE-22 改成了 Assumptions）——我第一次跑全量时 14 个 skip 里含这 8 条，**全绿的 BUILD SUCCESS 掩盖了 3 个 Failure**；起库后才暴露。

**修复方向**（三选一，按侵入性排序）：
- `RefreshTokenEntity.familyId` 改成 `String`，service 层 `familyId.toString()` / `UUID.fromString()` 转换（最小改动，牺牲一点类型语义）；
- 自定义 `UuidTypeHandler extends BaseTypeHandler<UUID>` 并在 entity 字段上 `@TableField(typeHandler = ...)` + mapper 注册；
- 引入支持 PG uuid 的 typehandler 依赖。
修完必须**起真库跑 SecurityChainTest** 验证（它就是为这种"单测 mock 不到的层"存在的），并把"`RefreshTokenServiceTest` mock 了 insert，覆盖不到参数绑定"写进该测试类注释，防止下一个人以为它测过。

**连带说明**：`RefreshTokenMapper` 的 `@Update` 手写 SQL（`claim`/`revokeFamily`）带 `@Param` 的 UUID 参数走的是另一个绑定路径，不一定同样炸——但既然 insert 炸了，整条链路从未端到端通过，`claim` 的 SQL 是否正确**当前未被任何测试真正验证过**（`RefreshTokenServiceTest` 里也是 mock）。

## P1 · 高优先级

### BUG-30 断线续传的前端半成品：服务端实现了，客户端从未调用

`QaController.resume`（`GET /api/qa/stream/{streamId}`）+ `QaStreamRegistry` 的补历史机制 + `replay-end` 事件协议——服务端完整。但 `web/src/` 里**没有任何代码调用它**（grep `stream/` 零命中）：前端 `askStream` 断线后直接抛"连接中断,未收到定稿"，用户看到失败，服务端缓冲里躺着的 final 事件 30 秒后蒸发。demo 时网络抖一下就是一次"白等 + 重问（再花一次模型调用费）"。

考虑到提交信息明确写"断线续传"，这是**承诺了但没接通的功能**——与 BUG-6（死配置）、BUG-8（model 过滤未兑现）同型。修法：`askStream` 的 catch 里带 streamId 调 resume 接口补 final；或者诚实化——在 handoff 里降级为"服务端能力预留，前端未接"。另注意：resume 需要知道 streamId，而前端目前没有消费 `open` 事件里的 streamId（`dispatch` 里没有处理 `open` 分支）。

### BUG-31 流式接口的认证续期缺口

`api.js` 的普通 `request()` 对 401 做了"静默 refresh + 重放"，但 `askStream()` 收到 401 直接 `clearSession + 跳登录`——**流式提问永远不会尝试续期**。访问令牌缩到 30 分钟后，用户挂着页面 31 分钟后提问（而不是点按钮的瞬间过期）就会莫名被踢出，比旧版（120 分钟 + 无刷新）更易触发。修法：401 时先 `tryRefresh()`，成功则重发流式请求一次。
