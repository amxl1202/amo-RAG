# 功能演进路线（对标同类开源 RAG 平台）

> 目标：把同类项目有的功能学过来，**且在每一处做得更可验证**。
> 前提：只学功能，不读它的源码；实现按本项目风格从零写（项目立身之本是独立实现）。
> 写于 2026-10-23，当前基线：203 个测试、59 条评估集、recall@5 1.0 / MRR 0.8483。

---

## 0. 三条纪律

1. **每加一项，必须能回答"它解决了什么真实问题"**。答不上来的不加——那是给简历堆名词。
2. **每加一项，必须留下可验证的东西**：一个新测试、一组评估数字、或一次压测结果。没有验证的功能等于没做。
3. **一次一批，做完能讲清再进下一批**。半成品堆三个不如完整做一个。

### A. SSE 流式输出 —— ✅ 已完成（2026-10-24）

> 实现要点：`HttpPoster.postStreaming`（default 方法，`BodyHandlers.ofLines`）→
> `DashScopeChatModel.stream`（不重试，理由见下）→ `AnswerGenerator.generate(prompt, onDelta)` →
> `QaService.ask(question, onDelta)` → `QaController` 的 `POST /api/qa/stream`（`SseEmitter` +
> **一条虚拟线程服务一条流**）+ `GET /api/qa/stream/{id}?lastEventId=` 续传。
> 前端 `api.askStream` 用 `fetch` + `ReadableStream` 手写 SSE 帧解析（不用 `EventSource`，因为它带不了
> `Authorization` 头）。新增 14 个测试（流式解析 8 + 缓冲 5 + 编排 1），全量 217 个通过。
> **未做端到端验证**：本机 Docker 未运行，SSE 的真实验证要等库起来。

**它的做法**：模型回复逐字推送到前端，零等待。

**我们的硬约束**：答案生成后要过**逐句自检**，自检才能决定哪句删掉、引用哪几条。
所以不能像它一样"边生成边定稿"——那样推出去的句子可能随后被删，等于自己打自己"可溯源"的脸。

**我们的做法（两段式流）**：
1. `event: delta` —— 生成阶段逐字推送，前端用浅色/斜体标"待校验"；
2. `event: final` —— 自检完成后推最终定稿文本 + 引用列表 + token/耗时，前端替换样式；
3. `event: error` —— 模型或自检失败，带可重试标记。

**改进点（它没有的）**：
- **`Last-Event-ID` 断线续传**：服务端把事件缓冲 30 秒，前端重连后只补增量，而不是重跑一次 3 秒的问答；
- **"待校验"状态本身是个产品决策**：让用户看见"这句话还没核对过"，比假装流式=可信更诚实。

**成本** 1.5 天（`SseEmitter` + 事件编码 + 前端增量渲染 + 断线重连）。
**面试讲法**：*"流式和逐句自检是冲突的，我的解法是两段式：先流式给体感，自检完成后推 final 覆盖。断线续传用一个 30 秒的事件缓冲。"*

### B. JWT 双令牌 + 轮换 —— ✅ 已完成（2026-10-24）

> 实现要点：`refresh_tokens` 表（只存 SHA-256 哈希、按 `family_id` 分组）→
> `RefreshTokenService`（签发 / 轮换 / 族级吊销）→ `AuthService.refresh/logout` →
> `AuthController` 用 `Set-Cookie` 下发 **httpOnly + SameSite=Strict + Path=/api/auth**；
> 访问令牌 TTL 从 120 分钟降到 **30**（生产可配置）。
> 抢占用 `UPDATE ... WHERE used_at IS NULL` 的条件更新，并发刷新只可能有一个成功。
> 前端：`tryRefresh()` 用共享 Promise 收敛并发（否则多个 401 会并发提交同一枚令牌，
> 被判成重放把用户踢下线）、401 后刷新并**重放原请求**、路由守卫里静默换令牌（刷新页面不掉登录）。
> 新增 9 个测试（服务层 8 + 真 HTTP 的轮换/重放 1），全量 226 个。
> **端到端未跑**：Docker 未启动，真库那条跳过。

**它的做法**：Access 15 分钟 + Refresh 存 httpOnly Cookie + 数据库 Rotation。

**我们的做法**：加 `refresh_tokens` 表（token_id / user_id / 过期 / 是否已用 / family_id），
`POST /api/auth/refresh` 换新 access + 新 refresh，旧 refresh 立即标记已用。

**改进点（它 README 只写了 rotation，没写盗用检测）**：
- **令牌族重放检测**：若一个已用过的 refresh 被再次提交，说明令牌可能被窃（合法用户和攻击者各持一份），
  此时**吊销整个 family 并强制重新登录**。这是 OAuth 2.0 安全实践里的标准做法，也是"轮换到底防住了什么"的完整答案。

**成本** 1 天（建表 + 签发/校验 + 3 个测试：正常轮换、旧令牌重放被拒、重放触发全族吊销）。
**面试讲法**：*"轮换本身不防重放，只有记录'是否已用'并做族级吊销才防得住。这条是我对比了几种实现之后补的。"*

### C. metrics + 成本画像 —— ✅ 已完成（2026-10-25）

> 实现要点：`qa_records` 表（生成/自检 token 分开存、两层耗时分开存）→ `QaRecordService`
> 异步写入（虚拟线程池，失败只记日志、不影响回答）→ `GET /api/metrics/summary?days=7`，
> SQL 里用 `count(*) FILTER` + `percentile_cont` 一次扫描出总数/三态计数/P50/P95/token 总量。
> 埋点只在接口层调用：评估跑批直接调 `QaService`，不污染线上口径。
> 价格从配置读（`app.metrics.input-price-per-1k` / `output-price-per-1k`），调价不改代码。
> 新增 5 个测试（拒答率与异常率分开、成本含自检、输入输出分价、空窗口、null 聚合），全量 231 个。
> **未做**：前端面板（接口已就绪）；端到端未跑（Docker 未启动）。

**它的做法**：AOP 切面记关键操作。

**我们的做法（不做泛泛的操作日志，做"回答成本画像"）**：
- 新表 `qa_records`：question / status / reason / prompt_tokens / check_tokens / retrieval_ms / answer_ms / citation_count / model；
- 写入点放在 `QaService` 返回处（一次 insert，异步，失败不阻塞回答）；
- `GET /api/metrics/summary` 返回：P50/P95 延迟、拒答率、平均引用数、token 总量与单题成本。

**改进点（它没有的）**：**埋点与评估基线打通**。
它有 metrics 但没有评估集，我们有评估集但没有线上数据——合起来才能回答
"线上拒答率 12% 是否正常"（对照评估集里的 10/59 ≈ 17%）。这是"可观测的 RAG"，不是"又一个日志表"。

**成本** 1.5 天（建表 + 异步写入 + 聚合查询 + 一个前端小面板可选）。
**面试讲法**：*"我不满足于记操作日志，我要知道每一题花了多少钱、慢在检索还是生成、拒答率离基线差多少。"*

### D. 租户隔离 —— ✅ 已实现（2026-10-25），**真库验证待补**

> 实现要点：`users` / `documents` 加 `tenant_id`（存量默认 1）；JWT 带 `tenant` 声明，
> `AuthPrincipal` 增加 `tenantId`；**检索链路的每个方法都加 `tenantId` 必填参数**（`ChunkSearcher` /
  `VectorStoreRepository` / `HybridRetriever` / `QaService.ask`）——让"忘了过滤"变成编译错误；
> 两路检索 SQL 都 `JOIN documents d ON d.id = c.document_id AND d.tenant_id = ?`。
>
> **顺手挖出一个泄漏点**：原来的 `UNIQUE (sha256)` 是全局的，B 传一份 A 已上传的文件会收到 409，
> 等于确认了"A 有这份文件"。已改成 `UNIQUE (tenant_id, sha256)`。
>
> 负向测试 5 条（`TenantIsolationTest`）：跨租户详情 404（且断言不是 403）、跨租户 ingest/vectorize 404、
> 检索通道不返回别的租户的切片（同一探针词租户二能查到，证明过滤条件真的生效而不是查了个空）、
> 去重键按租户、列表只含本租户。
>
> **已验证**：`REQUIRE_DB=1 mvn test` → 240 个全跑，0 失败 0 跳过。
> 过程中真库抓出两个问题：SQL 里插了 `tenant_id = ?` 但实参没跟着加（`未设定参数值 5`）；
> 以及我最初把"检索不跨租户"断言成"结果为空"——关键词通道是模糊匹配，
> 租户一里本来就有相似度够高的旧切片，那条断言失败的原因是相似度而不是隔离。
> 改成断言"不出现那条切片"，测试才真正测的是隔离。

**它的做法**：群组 + 邀请码 + 审批 + 检索时附加 `groupId` 过滤。

**我们的做法**：不做群组协作（那是产品功能），只做**租户隔离**：
`documents.tenant_id` + `document_chunks.tenant_id`，检索 SQL 强制带 tenant，登录用户绑定租户。

**改进点（它声称隔离，我们能证明隔离）**：
- 写**越权负向测试**：A 租户的令牌取 B 租户的文档 → 必须 **404 而不是 403**
  （403 等于告诉对方"这个 id 存在"）；
- 检索层同样要测：B 租户提问时，A 的切片**不得出现在候选里**（这条比接口鉴权更容易漏，因为 SQL 一忘就全泄漏）。

**成本** 2.5 天（DDL + 全链路过滤 + 4 个负向测试 + 现有数据回填）。
**面试讲法**：*"隔离不能只写在 README 里。我写了负向测试：跨租户访问必须表现为'不存在'，连检索候选里都不能出现。"*

### E. 查询规划（LLM 改写） —— 它有，我们没有

**它的做法**：用 LLM 做查询改写/规划再检索。

**我们的做法（评估驱动，而不是直接加）**：
1. 先扩评估集：加 15 条"问法与原文措辞差异大"的用例（现有 c48 的覆盖率只有 0.125，就是这类）；
2. 只加一路：把问题改写成"关键词式查询"再走关键词通道（向量通道不改）；
3. 跑同一套指标，**提升不到 3 个点就删掉**（模型非确定性带来的波动约 ±2%）。

**改进点**：它加了改写，我们**加了又敢删**。这条最有说服力——因为它证明的是判断力，不是功能清单。

**成本** 0.5 天实现 + 0.5 天评估。
**面试讲法**：*"我先测了再决定。改写让 recall 涨了 N 个点，但单题延迟 +1.2 秒、成本翻倍，最后我选择只在低置信度时触发。"*（真实结论以实测为准，不要预设）

### F. 四级证据评估 vs 我们的二值门控 + 自检

**它的做法**：四级充分度。

**我们的做法**：把当前"过/不过"升级成**四档 + 每档对应动作**：
| 档位 | 判据 | 动作 |
|---|---|---|
| 充分 | 至少 1 条高相似且自检通过率 ≥ 80% | 直答 |
| 部分 | 自检剔除了部分句子 | 答，并在答案里标注"材料对此只提到…" |
| 不足 | 门控拒绝或整段无支撑 | 拒答 |
| **矛盾** | 两条证据对同一问题给出相反结论 | **列出冲突并拒答**（"材料中存在两种说法"）|

**改进点（它 README 未提矛盾）**：**矛盾检测**。RAG 最坑的不是"没有答案"，而是"材料里有两个互相打架的答案"
而系统装作没看见。这一步只需在自检提示里加一类判定，成本低、差异大。

**成本** 1 天（分级 + 提示词 + 5 条针对性用例）。

### G. Elasticsearch + IK 分词 —— 我们有 pg_trgm，它用 ES

**不建议换引擎**：换掉要重跑 59 条基线，收益主要是名词。

**建议做的小实验（1 天）**：给 PostgreSQL 装 `zhparser` 或 `pg_jieba`，用**现有评估集**对比
`pg_trgm` 与中文分词的效果。若提升明显（>3 个点），留下；不明显，写成一条"测过但没必要"的记录。

**改进点**：它选了 ES 是因为默认假设"ES 更好"。我们用数据回答"在 42 个切片的量级上，ES 带来的收益是否值那一整套中间件"。

### H. 分片上传 + MinIO —— 它有，我们 50MB 上限本地存储

**不做**，除非出现真实需求（比如要传 200MB 扫描件）。届时动机应该是"文件大小需求"，不是"对标"。
成本 2 天（MinIO 接入 + 分片合并 + 断点续传状态）。

### I. ReactAgent + 三级记忆压缩 —— 它最重的一块（59 文件）

**不在这个项目里做**。理由：这是"另一个子系统"，硬塞进来会变成"接了框架跑通"，
而面试官对"Agent"的追问深度远高于"RAG"（工具调用边界、循环终止、状态持久化、失败回滚）。
真要做，另开一个项目，别稀释这个项目的可讲深度。

### J. 前端 TypeScript + Pinia

**建议只做 TS**（2 天，分批迁移，先迁 `api.js` 与 `chat` 相关模块）。
Pinia 收益不大——当前全局状态只有令牌与用户。

## 2. 三批路线（时间盒，按面试价值排）

| 批次 | 内容 | 天数 | 产出物（必须能拿出来） |
|---|---|---:|---|
| **第一批** | A 流式 + B 双令牌 + C metrics | **4** | 断线续传演示、family 吊销测试、成本画像接口 |
| **第二批** | D 租户隔离 + E 查询改写评估 + F 证据分级 | **4.5** | 4 个越权负向测试、改写的评估结论、矛盾检测用例 |
| **第三批** | G 分词对比 + J 前端 TS | **3** | 一张分词对比表、TS 迁移完成 |

每批结束的标准：`mvn test` 全绿 + 新增用例覆盖新行为 + `docs/` 里有一段"这批做了什么、数字如何"。

## 3. 面试怎么讲（比代码更重要）

**被问"你对标过什么项目吗"**——不要否认，直接说：
> "对标过同类的开源 RAG 平台，补了三块：流式输出、双令牌、线上埋点。但每块我都改了做法：
> 它的流式是纯推字，我有逐句自检，所以做成两段式；它的 refresh 只有轮换，我加了令牌族重放检测；
> 它的 metrics 是操作日志，我做的是和评估基线对得上的成本画像。"

**被问"哪些是你自己想加的"**——举两个"加了又删"的例子，这比堆功能有说服力：
1. 阈值门控：按计划做了，实测两组分布重叠，降级成兜底；
2. 查询改写：加了之后 recall 提升不够抵消延迟与成本，改成按需触发（或删掉）。

**不要说的话**："我照着 XX 项目做的"——功能可以参照，判断必须是自己的。

## 4. 明确不做的

- ReactAgent / 三级记忆压缩（另一个项目的量级）
- Elasticsearch（换引擎不换收益）
- 群组协作 / 邀请审批（产品功能，不是技术深度）
- MinIO 分片上传（没有 200MB 的场景）
- Pinia（全局状态只有两个字段）
