## 一、两层指标分开看，永远不合成总分

合成一个总分是评估里最常见的错误：分数掉了，你分不清是检索没找对地方，还是生成答坏了。
两层的分母都不同（检索 49 条正向，拒答 10 条文档外），本来就不可加。

### 1.1 检索层（49 条正向用例）

| 方案 | recall@5 | recall@20 | MRR | 首次未进前 20 的题数 |
|------|---------:|----------:|----:|---:|
| ILIKE（纯字串） | 0.9592 | 1.0000 | 0.8320 | 0 |
| TRGM（字串 ∪ 模糊） | 0.9592 | 1.0000 | 0.8320 | 0 |
| **VECTOR（纯语义）** | 0.9388 | 1.0000 | **0.7657** | 0 |
| HYBRID RRF k=0 | 0.9796 | 1.0000 | 0.8386 | 0 |
| HYBRID RRF k=20 | 0.9796 | 1.0000 | 0.8476 | 0 |
| **HYBRID RRF k=60** | **1.0000** | 1.0000 | **0.8483** | 0 |

> **向量通道的口径已核实（2026-10-21 晚补测）**：这张表里的 VECTOR 行是在
> `text_type` 未显式指定时测的。抽检同一段文本分别取 `text_type=query` / `document` / 不传，
> 三者向量余弦**全部为 1.000000**（前三维逐位相同）—— 当前专属实例的 `text-embedding-v3`
> 接受这个参数但不改变输出。所以 VECTOR 行没有被"查询侧被削弱"污染，本表不需要按两个口径分开标注。
> 接口仍已按查询/文档两侧拆开（`embedQuery` / `embedDocument`），防的是换模型或换供应商后默认值变化。

### 1.2 生成层（全链路）

| 指标 | 值 | 口径 |
|------|----|------|
| 引用正确率 | **0.8571**（96/112 条引用） | 引用到的切片里同时含该题全部期望词的比例；跨段落用例按"引用集合并集覆盖全部期望词"整题计 |
| 自检通过率 | **0.9677**（60/62 句） | 自检判定有材料支撑的句子比例。**判定者与被测者是同一个模型** —— 名字里刻意不出现“准确率” |
| 拒答准确率 | **1.0000**（10/10） | 文档外问题里被拒答的比例 |
| 误拒率 | **0.0000**（0/49） | 文档内问题里被拒答的比例 |
| 编造编号 | **0 次** | 被 `CitationParser` 剔除的、材料里不存在的编号总数 |
| 用量 | 86071 token / 109 秒 | **口径注意**：86071 只含生成那一次调用（自检调用的 token 当时被丢弃），109 秒则含两次调用。工具已修（`Verdict` 带自检用量，输出分列「生成 / 自检」），但本表未重跑 —— 重跑会得到更大的数字，且各项会随模型非确定性小幅变动 |

**同一套代码连跑两次的波动**（重要）：

| 指标 | 第一次 | 第二次 | 差 |
|------|---|---|---|
| 引用正确率 | 0.8661 | 0.8571 | 0.009 |
| 自检通过率 | 0.9841 | 0.9677 | 0.016 |

模型温度 0.2 仍非确定输出。**结论：小于约 2% 的变化不能当成"改好了"或"改坏了"。**
以后要判断一次改动是否有效，要么多跑几次取中位数，要么只信那种能拉开 5 个百分点以上的差异。

读法：

- **关键词通道明显受益**（0.9592 → 0.9796）：修复前 `alphabeta` 这种粘连让短语命中不了，
  段内换行又让"跨行的半句话"匹配不上；两处都在字面匹配上直接生效。

## 二、拒答阈值校准（这是本次最反直觉的一段）

计划里写的是"阶段一在检索后按相似度阈值直接拒答，省一次模型调用"。
**实测：这个做法在当前语料上不成立。**

### 2.1 两组分布

| 组 | 条数 | 向量 top-1 余弦 | 关键词覆盖率 |
|----|---:|----------------|-------------|
| 文档内问题 | 49 | 0.559 ~ 0.789 | 0.125 ~ 0.926 |
| 文档外问题 | 10 | 0.555 ~ 0.688 | 0.083 ~ 0.417 |

两组**完全重叠**：

- 文档外里相似度最高的 c57（`HNSW 的 ef_search 推荐取值`）是 0.688，
  比文档内最低的 c48（`什么情况下不允许开工`）的 0.559 还高 0.13；
- 关键词覆盖率同理：文档外最高 0.417，文档内最低 0.125。

也就是说，**任何单点阈值都会同时切掉两边的样本**。取 0.65 会把 c48、c42、c40 等
6 条文档内问题误拒；取 0.60 仍然误拒 3 条；取 0.55 则连一条文档外都拦不住。

### 2.2 为什么重叠

两个原因，都是这套语料的结构性特征：

1. **语料只有 42 片、覆盖了几乎所有话题**。中文技术笔记里"服务器型号""团队负责人"
   这类问题，字面上没有，但语义上离"参数速查""协作约定"这些章节很近 —— 向量相似度天然偏高。
2. **文档内问题的问法与原文措辞差异大的，覆盖率也很低**。c48 问"什么情况下不允许开工"，
   原文是"没有验收标准的板块不开工"，2-gram 只重合了很短的片段，覆盖率 0.125。

### 2.3 那阈值最后怎么定

**不取分界点，取"不会误拒"的下界**，并把它的实际作用说清楚：

```
min-vector-similarity = 0.35   # 低于全部 59 题的最低值 0.555
min-keyword-coverage  = 0.12   # 低于文档内最低值 0.125
```

两条判据是"或"的关系，于是**单条判据都不会误拒本评估集任何一题**。
代价是：**阶段一在这套语料上一次都不触发**（本次运行 0 次），拒答实际由
"模型自己说材料中未提及"承担（10/10 全部是 `MODEL_INSUFFICIENT`）。

它在代码里保留的理由只有一个：检索彻底失败时的兜底（库里没数据、两路都返回无关片段）。
**不要把它当成"省调用"的机制** —— 现在的数据不支持这个说法。

要让阶段一真正承担拒答，得换一个能把两组分开的信号（例如用小模型做一次
"这段材料能否回答该问题"的二分类），而不是继续在相似度上挪阈值。这条进想法池。

## 三、四条结论

**结论一：纯向量通道仍然最差，但差距缩小了。**

MRR 0.7657 对 0.8320（关键词），方向与上一版一致（0.8167 对 0.9167），
但**评估集从 10 条扩到 59 条之后，recall@5 不再全员满分**（0.9388 vs 0.9592），
指标第一次有了区分度。

**结论二：融合这次真的赢了，k=60 也有数据支撑了。**

上一版结论是"融合没超过关键词单独使用，只是不让弱通道拖后腿"，那是 8 条正向用例
撑不住结论。59 条上：

| | recall@5 | MRR |
|---|---|---|
| 关键词单独 | 0.9592 | 0.8320 |
| 融合 k=60 | **1.0000** | **0.8483** |

融合比任一单通道都好，且 k=0 < k=20 < k=60 单调递增 —— **论文默认的 60 在这个语料上
确实优于 0 和 20**。上一版"三组数字完全一致"是评估集太小导致的假象，已在
`docs/retrieval-comparison.md` 里追加修订说明。

**结论三：拒答准确率 10/10、误拒 0/49，但不能记在门控头上。**

全部由模型自述拒答。这个数字说明**提示词里那条"材料不足就输出材料中未提及"是有效的**，
说明不了阈值有效。评估报告里如果只写"拒答准确率 100%"，读者会以为是阈值调的，
这就是最容易做假的地方，所以必须写清归因。

**结论四：阶段二的收益很小。**

62 句里只剔掉 2 句。自检模型的判定与生成模型高度一致（同一个模型自查自己），
这符合预期但不构成独立证据 —— 想做真正的"答案支持率"，需要人工标注或换一个模型来判。
当前这个数只能读成"自家校验的通过率"。

## 四、局限（先说清，免得数字被高估）

1. **语料只有 2 份实质文档、42 个切片**，且 `rag-notes.pdf` 与 `rag-notes.docx` 是同一份
   内容的两种格式（各 8 片，内容重复）。真实语料的多样性远高于此。
2. **正负比 49:10**。文档外样本只有 10 条，拒答准确率的分辨率是 10% 一档。
3. **自检通过率由自检模型判定**，不是人工标注，存在自我一致性偏差。指标名已从“答案支持率”改掉，
   原因见《审核响应·第四批》第七节：一个需要现场免责声明的名字是错的名字。
4. **单次运行**。除注明波动的那两项外，其余指标只有一次采样。
5. 评估集的期望词必须落在同一行内 —— PDF 排版换行会把句子切断（见问题记录 P-23），
   跨行的短语不会命中，构建期望词时已经避开，但这也意味着**评估集对语料排版敏感**。
6. **`text_type` 在本次使用的实例上无效**（见 1.1 表下的补测）。这意味着
   "非对称检索的两侧区分"在这套环境里拿不到收益；换到公共 DashScope 或别的模型时，
   必须**重新抽检向量是否真的不同**，再决定要不要重跑基线。
