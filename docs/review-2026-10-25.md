## P0 · 登录与注册接口 100% 返回 500（已实证复现）

### BUG-29 MyBatis 缺 UUID TypeHandler，刷新令牌写入必炸

**现象**（起真实服务 `POST /api/auth/register`，curl 复现）：

```
{"code":500,"message":"服务内部错误"}    http=500
```

服务端堆栈（关键行）：

```
java.lang.IllegalStateException: Type handler was null on parameter mapping
for property 'familyId'. It was either not specified and/or could not be found
for the javaType (java.util.UUID) : jdbcType (null) combination.
  ... RefreshTokenMapper.insert
  ... RefreshTokenService.issue(RefreshTokenService.java:131)
  ... AuthService.issueSession → AuthService.register
```

**根因**：`RefreshTokenEntity.familyId` 类型是 `java.util.UUID`，而 MyBatis 默认没有注册 UUID → PostgreSQL `uuid` 的 TypeHandler。`mapper.insert(entity)` 在参数绑定时直接抛 `IllegalStateException`。

**影响面**：`register` / `login` 都要经 `issueSession → issueNewFamily → insert` —— **所有注册与登录全部 500**。刷新令牌功能整体不可用，`refresh` / `logout` 无从谈起。

**为什么 231 个测试没抓到** —— 两层漏检，都是测试策略的结构性盲区：

1. `RefreshTokenServiceTest`（8 条，全绿）**mock 了 RefreshTokenMapper** —— `mapper.insert` 被替换成桩，MyBatis 参数绑定这一层从未被走过；
2. 本该抓住它的 `SecurityChainTest`（真容器真 HTTP，`registerThenAccess` / `loginFailuresLookIdentical` / `refreshRotatesAndRevokesFamilyOnReplay` 三条恰好就是依赖注册成功的用例）在**数据库未启动时整类 skip**（第六批 ISSUE-22 改成了 Assumptions）——第一次跑全量是 `231 run, 14 skipped, BUILD SUCCESS`，**全绿掩盖了 3 个真实 Failure**；起库后才暴露。

**修复方向**（三选一，按侵入性排序）：

- `RefreshTokenEntity.familyId` 改成 `String`，service 层 `toString()` / `UUID.fromString()` 转换（最小改动）；
- 自定义 `UuidTypeHandler extends BaseTypeHandler<UUID>`，entity 字段 `@TableField(typeHandler = ...)` 并在 mapper 注册；
- 引入支持 PG uuid 的第三方 typehandler 依赖。

修完必须**起真库跑 SecurityChainTest** 验证（它就是为"单测 mock 不到的层"存在的），并把"该测试 mock 了 insert，覆盖不到参数绑定"写进 `RefreshTokenServiceTest` 类注释。

**连带说明**：`RefreshTokenMapper` 的 `@Update` 手写 SQL（`claim` / `revokeFamily`）走另一条参数绑定路径，不一定同样炸——但整条链路从未端到端通过，这些 SQL 的正确性**当前未被任何测试真正验证过**。

## P1 · 高优先级

### BUG-30 断线续传是半成品：服务端完整，客户端从未调用

`QaController.resume`（`GET /api/qa/stream/{streamId}`）+ `QaStreamRegistry` 补历史 + `replay-end` 事件协议——服务端全套齐全。但 `web/src/` 里**没有任何代码调用它**（grep `stream/` 零命中）：

- 前端 `askStream` 断线后直接抛"连接中断,未收到定稿"，用户看到失败；
- 服务端缓冲里的 final 事件 30 秒后蒸发；
- `dispatch` 里没有处理 `open` 事件的分支——**连 streamId 都没被消费**，续传无从做起。

提交信息明确写着"断线续传"——这是**承诺了但没接通的功能**，与 BUG-6（死配置）、BUG-8（model 过滤未兑现）同型。修法：`askStream` 断线时带 streamId 调 resume 补 final；或在 handoff 里诚实降级为"服务端能力预留，前端未接"。

### BUG-31 流式接口的认证续期缺口

`api.js` 的普通 `request()` 对 401 做了"静默 refresh + 重放"，但 `askStream()` 收到 401 直接 `clearSession + 跳登录`——**流式提问永远不会尝试续期**。访问令牌缩短到 30 分钟后，用户挂着页面 31 分钟后提问就会被莫名踢出，比旧版（120 分钟无刷新）更易触发。修法：401 时先 `tryRefresh()`，成功则重发一次流式请求。

## 历史审核修复的核实（本批一并验证）

- **第六批 ISSUE-21（Filter 双注册）**：`FilterRegistrationBean.setEnabled(false)` 落地，JwtAuthFilter 类注释写明"只能注册一次"的因果链——修法与建议一致；
- **第六批 ISSUE-22（测试口径矛盾）**：SecurityChainTest 改为条件跳过（`DatabaseAvailableCondition`），两套哲学统一。**但本批证明 skip 有代价**：能端到端抓 BUG-29 的唯一三类用例恰好是最容易被 skip 的。建议补一条"CI 必须带库跑一次"的约定；
- **10-22 审核（N1~N23）的 6 个 P1**（`0f91af9`）：逐项读过 diff 并验证——`keptLabels` 过滤引用（连 CHECK_UNAVAILABLE 时给全集保持引用不缩水的边界都处理了）、BCrypt 按字节校验给出"约 24 个汉字"的可执行提示、异常分类 4xx/5xx、白名单收窄成具体路径（`GET /api/auth/login` 得 405 而非误导性 401）、N9/N18/N19 顺手收掉。质量高。

## 值得肯定（修复时不要顺手改掉）

- **RefreshTokenService 的轮换设计本身是对的**：条件更新 `claim`（`UPDATE ... WHERE used_at IS NULL`）原子抢占、重放检测吊销整族、SHA-256 存哈希不存原文——设计无可挑剔，只是栽在 ORM 类型绑定这个工程细节上，修好 BUG-29 即活；
- cookie 策略（httpOnly + SameSite=Strict + path 限定 `/api/auth`）与"为什么不给 refresh 配 CSRF"的三条理由论证充分；
- 前端 `tryRefresh` 的共享 Promise 并发收敛——注释明确写了"并发提交同一枚刷新令牌会被判重放踢下线"，这个坑他们自己想到了；
- `DashScopeChatModel.stream` 的"不重试，已推出的增量收不回"论证、`stream_options.include_usage` 防成本少算（与 N4 同源的坑记住了）；
- 前端自解析 SSE 帧的 `buffer + \n\n` 切分正确处理跨 TCP 包；"不用 EventSource、不把令牌塞 URL"的理由链完整。
