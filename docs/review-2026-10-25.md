## P0 · 登录与注册接口 100% 返回 500（已实证复现）

### BUG-29 MyBatis 缺 UUID TypeHandler，刷新令牌写入必炸

**现象**（起真实服务 `POST /api/auth/register`，curl 复现）：

```
{"code":500,"message":"服务内部错误"}    http=500
```

服务端堆栈（关键行）：

```
java.lang.IllegalStateException: Type handler was null on parameter mapping
for property 'familyId'. It was either not specified and/or could not be found
for the javaType (java.util.UUID) : jdbcType (null) combination.
  ... RefreshTokenMapper.insert
  ... RefreshTokenService.issue(RefreshTokenService.java:131)
  ... AuthService.issueSession → AuthService.register
```

**根因**：`RefreshTokenEntity.familyId` 类型是 `java.util.UUID`，而 MyBatis 默认没有注册 UUID → PostgreSQL `uuid` 的 TypeHandler。`mapper.insert(entity)` 在参数绑定时直接抛 `IllegalStateException`。

**影响面**：`register` / `login` 都要经 `issueSession → issueNewFamily → insert` —— **所有注册与登录全部 500**。刷新令牌功能整体不可用，`refresh` / `logout` 无从谈起。

**为什么 231 个测试没抓到** —— 两层漏检，都是测试策略的结构性盲区：

1. `RefreshTokenServiceTest`（8 条，全绿）**mock 了 RefreshTokenMapper** —— `mapper.insert` 被替换成桩，MyBatis 参数绑定这一层从未被走过；
2. 本该抓住它的 `SecurityChainTest`（真容器真 HTTP，`registerThenAccess` / `loginFailuresLookIdentical` / `refreshRotatesAndRevokesFamilyOnReplay` 三条恰好就是依赖注册成功的用例）在**数据库未启动时整类 skip**（第六批 ISSUE-22 改成了 Assumptions）——第一次跑全量是 `231 run, 14 skipped, BUILD SUCCESS`，**全绿掩盖了 3 个真实 Failure**；起库后才暴露。

**修复方向**（三选一，按侵入性排序）：

- `RefreshTokenEntity.familyId` 改成 `String`，service 层 `toString()` / `UUID.fromString()` 转换（最小改动）；
- 自定义 `UuidTypeHandler extends BaseTypeHandler<UUID>`，entity 字段 `@TableField(typeHandler = ...)` 并在 mapper 注册；
- 引入支持 PG uuid 的第三方 typehandler 依赖。

修完必须**起真库跑 SecurityChainTest** 验证（它就是为"单测 mock 不到的层"存在的），并把"该测试 mock 了 insert，覆盖不到参数绑定"写进 `RefreshTokenServiceTest` 类注释。

**连带说明**：`RefreshTokenMapper` 的 `@Update` 手写 SQL（`claim` / `revokeFamily`）走另一条参数绑定路径，不一定同样炸——但整条链路从未端到端通过，这些 SQL 的正确性**当前未被任何测试真正验证过**。

## P1 · 高优先级

### BUG-30 断线续传是半成品：服务端完整，客户端从未调用

`QaController.resume`（`GET /api/qa/stream/{streamId}`）+ `QaStreamRegistry` 补历史 + `replay-end` 事件协议——服务端全套齐全。但 `web/src/` 里**没有任何代码调用它**（grep `stream/` 零命中）：

- 前端 `askStream` 断线后直接抛"连接中断,未收到定稿"，用户看到失败；
- 服务端缓冲里的 final 事件 30 秒后蒸发；
- `dispatch` 里没有处理 `open` 事件的分支——**连 streamId 都没被消费**，续传无从做起。

提交信息明确写着"断线续传"——这是**承诺了但没接通的功能**，与 BUG-6（死配置）、BUG-8（model 过滤未兑现）同型。修法：`askStream` 断线时带 streamId 调 resume 补 final；或在 handoff 里诚实降级为"服务端能力预留，前端未接"。

### BUG-31 流式接口的认证续期缺口

`api.js` 的普通 `request()` 对 401 做了"静默 refresh + 重放"，但 `askStream()` 收到 401 直接 `clearSession + 跳登录`——**流式提问永远不会尝试续期**。访问令牌缩短到 30 分钟后，用户挂着页面 31 分钟后提问就会被莫名踢出，比旧版（120 分钟无刷新）更易触发。修法：401 时先 `tryRefresh()`，成功则重发一次流式请求。

## 本批新发现

### ISSUE-37 ingest/vectorize 的租户校验依赖 controller 前置检查（P2，防御纵深缺口）

`DocumentController` 先 `documentService.getById(id, principal.tenantId())` 再调 `ingestService.ingest(id)` / `vectorizeService.vectorize(id)`——**校验与操作分离**。当前 controller 写法正确，无漏洞；但 `IngestService.ingest` / `VectorizeService.vectorize` 是公开 service 方法，不接收 tenantId、内部不校验——任何新调用点（恢复逻辑、定时任务、未来的内部 API）直接调它们就绕过租户检查。这与检索链路"tenantId 必填参数让忘了过滤变成编译错误"的做法不一致：检索层做到了防御纵深，文档操作层还是单点防线。

修法：`ingest(documentId, tenantId)` / `vectorize(documentId, tenantId)` 把 tenantId 传进 service，内部先按 (id, tenantId) 查文档——与 `DocumentService.getById` 同一模式。改动小，建议下一批顺手。

### ISSUE-38 qa_records 不带 tenant_id（P3）

成本画像表没有租户维度——多租户上线后"按租户看成本"要靠推断。趁表还年轻加一列（DEFAULT 1），比事后迁移便宜。

### ISSUE-39 内容寻址存储与租户去重的将来冲突（P3，设计备忘）

物理文件按 `{sha256}.{ext}` 全局寻址：两个租户上传同一份文件共用同一个物理路径。当前无删除接口所以无冲突；**将来实现"删除文档 + 物理删文件"时，会砸到另一个租户的同内容文件**。到时的正确做法是引用计数或"最后引用才删文件"——先记在这里，防止到时按直觉写成直接 delete。

（P2-19 的 post-filter 问题在叠加 tenant 过滤后依然存在——`ORDER BY <=>` 先取回再过滤 tenant/model，返回可能不足 limit。已知登记，不重复展开。）

- **超出建议的细节**：启动恢复 `recoverStuckDocuments` 是跨租户运行的，`trigger` 现在传**文档自己的 tenant**（`document.getTenantId()`），而不是硬编码系统租户——提交信息写得很清楚："恢复逻辑不该拥有跨租户的写权，它只是替这份文档重跑一次它本来就该做的事"。测试专门断言了 tenantId=2 的文档恢复后不会静默卡死。这是审核建议没有覆盖到的正确推论；
- `recordAsync` 签名加 tenantId——编译期强制两个调用点（流式/非流式）都传，与检索链路同构。

## 2. ISSUE-38 修复核实 —— 到位，且严重度判断被纠正

- `qa_records` 加 `tenant_id`（默认 1）+ `(tenant_id, created_at)` 索引；`MetricsMapper.summarize` 加 `WHERE tenant_id = ?`；`MetricsController` 从 principal 取租户；
- **响应方对严重度的反驳成立**：原审核标 P3 的理由是"趁表年轻加列便宜"——但响应方指出**原实现对任何登录用户返回全平台的题量、拒答率与成本**：明细越权会被 404 挡住，**聚合越权只会安静地把别家的用量告诉你**，不报任何错。聚合泄漏比明细泄漏更隐蔽，优先级应当对齐 ISSUE-37。接受。
- 新测试 `metricsAreTenantScoped` 的断言手法值得记录：造一条 token=999999 的"一眼能认出来"的租户 2 记录，断言租户 1 的汇总不含它、租户 2 的含它——**同时验证了"过滤生效"和"不是查了个空"**，比只断言 doesNotContain 严谨。

## 3. P2-19 的反驳 —— 部分成立，接受"当前无问题"的结论

**响应方的主张**：P2-19 说"ORDER BY 先取回再过滤"，但 SQL 的 WHERE 在 ORDER BY/LIMIT 之前；实测 42 条切片时规划器选 Seq Scan，不存在"返回不足 limit"。真风险是数据量增长后规划器切到 HNSW index scan——0.8.3 的 `hnsw.iterative_scan` 是缓解开关。

**审核方裁决**：
- **技术层面他们是对的**：SQL 文本顺序不决定执行顺序，规划器才决定；42 行时 Seq Scan 意味着过滤在排序前完成，当前无 shortfall。原意见的表述（"叠加 tenant 后依然存在"）没有区分当前与未来，应改为"**规划器切换到索引扫描时风险重现**"；
- **一个保留**：切换点是**不可见的**——表涨过某个阈值后行为静默改变，没有报错，表现仍是"返回不足 limit 条"。响应方已在提交信息里点名 `hnsw.iterative_scan`，建议在 handoff 里补一行监控口径："切片数过万或出现'检索结果不足 limit'的反馈时，检查 EXPLAIN 是否已切到 Index Scan，并评估打开 iterative_scan"。到那一步之前，本条挂账关闭。
